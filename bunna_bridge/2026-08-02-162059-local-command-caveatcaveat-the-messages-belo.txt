● Both exploration agents are done, and I've read the core files myself. Here's
  the grounded picture and a plan.

  What exists today

  - Roaster is a first-class User.Role, but purely as a buyer-equivalent with an
  editable profile (MyRoastery.tsx) — read-only marketplace access, offers,
  sample requests. No operational tooling.
  - Exporter "Pipeline" (LotPipeline.tsx) is a simple 4-stage Kanban (draft → 
  listed → contracted → exported) driven by a status field on CoffeeLot, gated
  by a set of boolean compliance flags (export_ready = all gates true) and
  enforced server-side in LotStatusUpdateView.
  - Washing station exists only as free text on CoffeeLot.washing_station — no
  structured entity a roaster (or anyone) could own/operate.
  - Certifications don't exist anywhere as a model. CoffeeLot has three
  standalone booleans (is_organic, is_fair_trade, is_rainforest_alliance) but
  nothing tracking cert body, number, or expiry — and compliance docs (phyto,
  EUDR DDS, etc.) are bespoke FileFields directly on the lot, not a reusable
  document/cert table.
  - Nothing exists for roasting itself: no batch, machine, or roast-step model
  of any kind.

  Proposed feature plan

  Key architecture decision first: you said roasters "usually have washing
  stations and usually export" — meaning many roaster-users are really dual-role
  (they process/export green coffee and roast it). I'd recommend extending lot 
  ownership/export rights to the roaster role rather than building a parallel
  lot-like model for washing stations — it reuses the compliance-gate machinery,
  EUDR DDS generation, and document-upload pattern that's already built and
  battle-tested, instead of duplicating it. A roaster who exports becomes,
  functionally, an exporter who also roasts.

  A. Roaster-as-exporter / washing-station operations (reuses existing Pipeline)
  1. Let role == "roaster" own/create CoffeeLots (extend IsExporterOrReadOnly,
  get_queryset, LotStatusUpdateView permission checks)
  2. Promote washing_station from free text to a structured WashingStation model
  (name, location, capacity_kg_per_day, owner FK)
  3. Surface the existing Lot Pipeline board for roaster-owned lots (nav change
  only — the board itself needs no new code)

  B. In-house roasting workflow (net new)
  4. RoastEquipment model — name, machine type (drum/fluid-bed/etc.), brand,
  batch capacity, install date
  5. RoastBatch model — green lot(s) in, batch code, roast date, machine used,
  input/output weight (loss %), roast level, key roast-curve points (charge
  temp, first-crack time/temp, development time, drop temp)
  6. A roast-batch board mirroring the Lot Pipeline pattern: Queued → Roasting →
  Resting → QC → Packaged → Shipped
  7. QC step reusing (or extending) the existing generic CuppingScore model
  against the roasted batch

  C. Certifications (net new, greenfield — built generically so it serves
  exporters, roasters, and washing stations alike)
  8. Certification model — holder, cert type
  (organic/fair-trade/rainforest-alliance/Q-Arabica/ISO/HACCP/other), issuing
  body, number, issue/expiry date, file (reusing the existing
  document_extension_validator/size-limit pattern)
  9. Certification management UI with expiry tracking/alerts
  10. Surface certs as trust badges on public roaster/lot-story pages — ties
  into the D2C storytelling angle

  D. Roaster ops dashboard — active batches, green-coffee inventory, cert expiry
  alerts, pipeline summary; new nav entries in AdminSidebar.tsx/SiteHeader.tsx.

  Suggested phasing: Certifications (self-contained, no dependencies) →
  roaster-as-exporter permission extension → roast batch/equipment tracking → QC
  + dashboard rollup.

  Before I design the architecture, four things only you can call

  1. Does every roaster get export/washing-station rights, or only some? If only
  some, we need a flag (e.g. roaster_also_exports) rather than a blanket
  permission change.
  2. Roast curve depth — simple fields (roast level, total time, drop temp) or a
  full time-series curve (multiple timestamped readings)? Big complexity
  difference.
  3. Can a RoastBatch blend multiple green lots, or is it strictly one lot in →
  one batch out? Blending is realistic for roasters but complicates traceability
  math.
  4. Should the existing is_organic/is_fair_trade/is_rainforest_alliance 
  booleans on CoffeeLot be replaced by real Certification records, or left alone
  with Certification as an additive layer?

  Once you weigh in on those, I'll move to architecture design (Phase 4) with
  concrete file-level changes.
